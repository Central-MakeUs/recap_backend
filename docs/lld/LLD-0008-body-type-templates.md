# LLD-0008: body 유형별 구조화 템플릿 (프롬프트 개정)

> Low-Level Design. 기능 구현 전 설계를 기록한다.

| 항목 | 값 |
| --- | --- |
| 상태 | Accepted |
| 날짜 | 2026-07-20 |
| 관련 | [ADR-0011](../adr/ADR-0011-infocard-flat-summary-fields.md), [LLD-0003](LLD-0003-ai-image-analysis-module.md)(프롬프트 대체), [LLD-0007](LLD-0007-search-api.md) |

## 맥락 (Context)

`CardSummary`/`JobSummary` 등 9개 레코드로 유형별 구조화 필드를 DB
컬럼 레벨에서 다시 도입하는 방안을 검토했으나(ADR-0011의 두 번째
재검토), **body를 여전히 평문 String으로 유지하되, 그 문자열 내부를
유형별 템플릿으로 구조화**하는 방향으로 최종 확정했다. DB 스키마·검색
쿼리(ADR-0014)를 전혀 건드리지 않고 프롬프트 변경만으로 구현 가능해
비용이 가장 낮다고 판단했다.

또한 검색 결과에서 body 매칭 시 발췌를 보여줄지(LLD-0007이 이미
`extractedText` 전용으로 만들어둔 `excerptOcrMatch` 확장 여부)를
확정했다.

## 결정 (Decision)

### `CardSummary` 및 9개 구현체는 삭제한다

ADR-0011에서 "미래에 재도입할 수 있게 코드는 보존한다"고 남겨뒀던
`CardSummary` 인터페이스와 `JobSummary`/`ShoppingSummary`/`PlaceSummary`/
`ScheduleSummary`/`KnowledgeSummary`/`ContentSummary`/`BenefitSummary`/
`RecordSummary`/`EtcSummary`, `CardSummaryConverter`를 전부 삭제한다.

이번이 **두 번째 재검토**이고, 이번엔 실제로 검토한 뒤 다른 방향(body
내부 텍스트 구조화)을 확정했다 — 즉 "아직 필요 없어서 미룬다"가 아니라
"검토했고 이 방향이 아니다"로 결론이 났으므로, 계속 남겨두면 죽은
코드가 영구히 남는다. 삭제해도 근거는 ADR-0002/ADR-0011/본 문서에
보존된다.

### body는 여전히 평문 String — 내부만 3블록 구조로 템플릿화

```
InfoCard.body 컬럼/타입/길이 제약 변경 없음
GeminiImageAnalysisProvider의 response_schema도 변경 없음
  (body는 여전히 "type": "STRING" 하나)
```

**볼드·마크다운·하이라이트 같은 리치 텍스트 서식은 전혀 쓰지 않는다.**
순수 텍스트 안에서 줄바꿈·빈 줄·`-`(불릿)·`"`(인용)만으로 구조를
표현한다.

```
라벨: 값          ← ① 핵심값 블록 (유형별 고정 라벨·순서)
라벨: 값

섹션명            ← ② 상세 블록 (유형별 고정 섹션명, 빈 줄로 구분)
- 항목
- 항목

원문              ← ③ 인용 블록 (CONTENT/RECORD만 사용)
"인용 문장"
```

각 유형의 정확한 라벨·섹션명·필수값은 아래 "5. 유형별 템플릿" 참고
(원본: `docs/prompt/card-type-classification-criteria.md`의 "5. 유형별
고정 항목" 표를 프롬프트 문구로 그대로 옮김).

### `BODY_MAX_LENGTH`를 500 → 1000으로 확정

기존 LLD-0003의 "후속/미결정" 항목이었던 임시값을 이번에 확정한다.
KNOWLEDGE(분량 제한 없음), RECORD(원문에 따름) 두 유형은 여전히 가끔
잘릴 수 있음을 인지하고, **배포 후 관찰 1순위 항목**으로 남긴다(아래
후속 참고).

### body 매칭 시 검색 결과 발췌 — 하지 않는다 (확정)

LLD-0007의 `excerptOcrMatch()`(현재 `extractedText` 전용)를 `body`
매칭까지 확장하지 않는다. body에서만 매칭된 검색 결과는 지금처럼
발췌·하이라이트 없이 카드만 노출된다.

**이건 검색 결과 화면의 `<mark>` 하이라이트(LLD-0007)와는 다른
결정이라는 걸 명확히 한다** — LLD-0007의 title/summary 하이라이트,
extractedText 발췌 기능은 이번 결정과 무관하게 그대로 유지된다. 이번에
정한 건 "body 안 텍스트에 서식을 안 넣는다"는 것과 "body 매칭 시
발췌를 안 보여준다"는 것, 두 가지뿐이다.

**따라서 `SearchHighlighter`, `SearchService`에는 코드 변경이 없다.**

### 유형 분류 기준 및 헷갈리는 유형 구분

`docs/prompt/card-type-classification-criteria.md`의 1~3번 섹션(핵심
신호, 인접 유형 구분선, 기록/캡처↔기타 경계)을 프롬프트에 그대로
반영한다. 상세는 그 문서 참고, 이 LLD에서 반복하지 않는다.

### 프롬프트 전문 (확정본)

```
당신은 사용자가 저장한 스크린샷 이미지를 분석해서, 나중에 쉽게 다시
찾아볼 수 있는 정보 카드로 정리하는 어시스턴트입니다.

이미지를 분석해서 아래 형식의 JSON으로만 응답하세요. 다른 설명이나
문장은 절대 추가하지 마세요.

{
  "type": "JOB | SHOPPING | PLACE | SCHEDULE | KNOWLEDGE | CONTENT | BENEFIT | RECORD | ETC 중 하나",
  "title": "핵심 내용을 요약한 제목",
  "summary": "한 줄 요약",
  "body": "아래 유형별 템플릿에 맞춰 구조화한 본문",
  "extractedText": "이미지에 보이는 모든 텍스트 원문"
}

## 1. 유형(type) 분류 기준

아래 9개 중 정확히 1개를 선택하세요.

- JOB(채용/취업): 특정 회사명+직무명이 함께 등장, "채용", "모집공고",
  "지원하기", "경력/신입", 잡코리아·원티드·사람인·링크드인 류 UI
- SHOPPING(쇼핑/상품): 가격 표시, "장바구니", "구매하기", 배송 정보,
  쿠팡·당근마켓·무신사 류 UI
- PLACE(장소/맛집): 지도, 위치 핀, 주소, 영업시간, 리뷰·별점,
  네이버지도·카카오맵·망고플레이트 류 UI
- SCHEDULE(일정/예약): 날짜+시간이 명확, "예약 완료", "예약번호",
  티켓·캘린더 UI
- KNOWLEDGE(정보/지식): 설명글, 뉴스, 블로그, "~하는 법", "~란?",
  특정 거래·장소·일정과 무관한 일반 정보
- CONTENT(책/콘텐츠): 책·영화·음악·드라마 제목, 저자·감독·아티스트명,
  넷플릭스·유튜브·스포티파이·교보문고 류 플랫폼, 평점
- BENEFIT(혜택/이벤트): "쿠폰", "할인코드", "이벤트 참여", "응모",
  조건부 혜택(첫 구매, 멤버십 등급)
- RECORD(기록/캡처): 카카오톡·문자 대화, 메모, 개인적 다짐·일기,
  명확한 분류 목적이 없는 개인 기록
- ETC(기타): 위 8개 중 어디에도 명확히 속하지 않는 경우 (fallback)

### 헷갈리는 유형 구분

- 채용/취업 vs 정보/지식: 특정 회사의 실제 채용공고면 채용/취업,
  "이력서 작성법" 같은 일반 조언/가이드면 정보/지식
- 쇼핑/상품 vs 혜택/이벤트: 화면의 주인공이 상품 자체(할인은
  부가정보)면 쇼핑/상품, 주인공이 할인/쿠폰 자체(상품은 부가정보)면
  혜택/이벤트
- 장소/맛집 vs 일정/예약: 아직 확정 안 된 탐색 단계면 장소/맛집,
  이미 확정된 예약/약속(예약번호 존재)이면 일정/예약
- 정보/지식 vs 책/콘텐츠: 개념·방법을 설명하면 정보/지식, 특정
  창작물(책·영화·음악) 자체를 소개하면 책/콘텐츠

### 기록/캡처 vs 기타

내용 자체는 뚜렷하지만(누가 봐도 무슨 내용인지 알 수 있음) 다른 8개
유형 어디에도 안 맞으면 기록/캡처. 핵심 정보 자체가 안 보이거나
판단이 불가능하면 기타.

## 2. title / summary 작성 규칙

- title: 이미지의 핵심 내용을 나타내는 제목. 1자 이상 30자 이내.
  줄바꿈 없이 한 줄로 작성하세요.
- summary: title보다 조금 더 구체적인 한 줄 요약. 80자 이내. 줄바꿈
  없이 작성하세요. body 첫 줄과 내용이 겹치지 않게 하세요.

## 3. body 작성 규칙 (가장 중요)

body는 볼드·마크다운 같은 서식 없이 순수 텍스트로 작성하되, 아래
구조를 반드시 지키세요. body는 최대 {BODY_MAX_LENGTH}자 이내로
작성하세요.

### body 구조 (3개 블록을 이 순서로 조합, 없는 블록은 생략)

라벨: 값
라벨: 값

섹션명
- 항목
- 항목

원문
"인용 문장"

- 핵심값 블록: "라벨: 값" 형식, 한 줄에 하나. 항상 body 최상단에,
  아래 유형별 템플릿에 정해진 라벨과 순서 그대로 사용. 값은 문장이
  아니라 구 단위로 작성.
- 상세 블록: 핵심값 블록과 빈 줄로 구분. 첫 줄에 섹션명만 단독으로
  적고, 그 아래 "-"로 시작하는 불릿을 나열. 아래 유형별 템플릿에
  정해진 섹션명을 정확히 그 문자열 그대로(띄어쓰기 포함) 사용.
  섹션이 여러 개면 섹션 사이도 빈 줄로 구분.
- 인용 블록: 원문 보존이 필요한 유형(CONTENT, RECORD)에서만 사용.
  섹션명은 CONTENT는 "인용", RECORD는 "원문"으로 각각 고정. 다음 줄에
  큰따옴표로 감싼 문장 하나.

### 값 표기 규칙

- 날짜: "2026-07-26 (일)" 형식. "내일", "D-3" 같은 상대 표현은
  절대값으로 변환하고, 변환이 불가능하면 원문을 그대로 쓰세요.
- 시간: "HH:MM" 형식 (예: "15:00")
- 가격: "39,900원 (32% 할인)" 형식처럼 할인율이 있으면 괄호로 병기
- 외국어는 한국어로 정리하되, 고유명사와 원문 인용은 원어를 유지

### 예외 처리

- 핵심값이 이미지에 없으면 해당 줄을 생략하세요. 추측하거나 빈
  값으로 채우지 마세요.
- 유형의 필수값(아래 템플릿 참고)이 이미지에 없으면, 그 유형으로
  분류하지 말고 ETC로 재분류하세요.
- 상세 블록에 넣을 내용이 없으면 그 블록 전체를 생략하세요.
- 화면이 두 유형에 걸치면 저장 목적에 더 가까운 쪽으로 분류하고,
  나머지 정보는 body 안에 자연스럽게 포함하세요.
- 전화번호, 주소, 예약번호처럼 사용자가 재확인하려고 저장했을 정보는,
  아래 템플릿에 없는 항목이어도 라벨을 새로 만들어서라도 핵심값
  블록에 포함하세요.

## 5. extractedText 작성 규칙

이미지에 보이는 텍스트를 최대한 빠짐없이 그대로 옮겨 적으세요. 이
필드는 검색용으로만 쓰이며 사용자에게 보이지 않습니다. body처럼
재구성하지 말고, 원문 그대로 나열하세요.

## 주의사항

- 반드시 위 JSON 형식으로만 응답하세요. 코드블록이나 다른 설명 문장을
  포함하지 마세요.
- 이미지 내용이 불분명하거나 텍스트가 거의 없는 경우에도, 보이는
  정보만으로 최선을 다해 채우세요.
```

`{BODY_MAX_LENGTH}`는 기존과 동일하게 Java 상수(1000)로 치환된다.

## 고려한 대안 (Considered Options)

1. **`CardSummary` 다형성 JSON으로 DB 컬럼 레벨 구조화 (기각)** — 검색
   쿼리(ADR-0014, `LIKE` 기반 평문 검색)와 정면 충돌, InfoCard 스키마
   변경 필요, 비용이 훨씬 큼.
2. **body 안 리치 텍스트 서식(마크다운) 허용 (기각)** — 클라이언트
   렌더링 파싱 부담, 서버/AI가 서식 문법을 완벽히 지킨다는 보장 없어
   깨진 서식이 그대로 노출될 위험.
3. **body 매칭 시에도 발췌·하이라이트 (기각, 이번엔 명시적으로)** —
   구현 비용 대비 이번 결정(body 내부 라벨 텍스트가 반복적이라 발췌가
   오히려 혼란을 줄 수 있음, 아래 후속 참고)에서 실익이 낮다고 판단.
4. **body 내부 3블록 텍스트 구조화 (채택)** — DB/검색 쿼리 변경 없이
   프롬프트만으로 구현 가능, 비용이 가장 낮음.

## 결과 (Consequences)

### 긍정
- InfoCard 스키마, 검색 쿼리(ADR-0014), 검색 하이라이트 로직
  (LLD-0007) 전부 무변경 — 변경 범위가 프롬프트+상수 하나로 국한됨.
- `CardSummary` 죽은 코드 삭제로 코드베이스 혼란 요인 제거.

### 부정 / 트레이드오프
- body가 이제 예약번호·가격 같은 실질적 검색 대상 정보를 더 많이
  담게 되는데, 검색 결과 화면에서 "왜 이 카드가 매칭됐는지"가 여전히
  안 보임(발췌 안 하기로 확정) — UX상 아쉬움이 있으나 지금은 감수.
- 라벨 문자열("가격:", "마감일:" 등)이 여러 카드에 반복적으로
  등장해, 이 라벨 자체로 검색했을 때 무관한 카드가 다수 매칭될 수
  있음(오탐 가능성).
- LLM이 라벨·섹션명 문자열을 프롬프트 지시와 정확히 똑같이(띄어쓰기
  포함) 지킬지는 실제로 관찰해야 함.
